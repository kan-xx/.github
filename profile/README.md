## 核心技术路线与设计考量：为什么我们不走“改内核/固件重刷硬件”路线？

目前开源社区对索尼微单固件的改造方案（无论是早期的 `fwtool` 解包重刷、硬件编程器/飞线 UART，还是近年针对新机型的 `BODYDATA.DAT` 自定义刷机包），普遍采用**“静态修改内核镜像或原厂核心库（如 `appFw.so`）指令字节 + 替换签名公钥重刷内部闪存分区”**的模式。

`kan-xx` 探索并工程化落地了一条完全不同的系统级路线：**不对闪存上的内核镜像与原厂核心库可执行代码做一字节篡改，而是通过模块化外挂加载器，在系统运行态内存（RAM）与动态内核模块层完成精准打补丁（Patch / Hook），并辅以机内自包含的事务回滚与硬件失效隔离机制。**

| 对比维度 | 传统/主流固件破解方案（静态改包 + 烧录硬件闪存） | `kan-xx` 技术路线（外挂动态底座 + 运行态内存/内核补丁） |
| :--- | :--- | :--- |
| **原厂内核与核心库改动** | 直接改写内核镜像（`uImage`）或原厂 `.so` 机器码指令，替换 RSA 密钥后重刷 `nflash` 分区 | **内核分区镜像、RTOS 固件与原厂核心库的磁盘可执行代码段 100% 零字节改动** |
| **补丁注入与生效时机** | **离线静态落盘固化**：刷写修改版固件覆盖原厂程序，多以修改机型判断宏解锁同平台隐藏代码为主 | **运行态内存动态干预**：仅对注册表库追加纯数据描述符以合法加载自研模块；用户态走 RAM 内 GOT 替换与回调接管，内核态走动态 `insmod` `.ko` 探针（断电即无痕消失） |
| **防变砖与故障恢复** | 强依赖拆机焊接主板微型 UART 串口，或使用外部硬件短接器拉入底层 `Fastboot` 刷回备份 | **纯软件自闭环免拆机防砖**：独创早期 `a7r-boot-guard` 双槽 SHA-256 事务守护（60s 未就绪自动回滚原厂）+ `nlink >= 1` 映射保留原子替换 |
| **验证方法与开源合规** | 依赖静态反编译猜测 + 真机刷写试错；分发修改版固件易触碰专有软件版权红线 | **跨 ARM / Thumb RTOS / MIPS32 原码无桩执行（Stub-Free Unicorn）先验排雷**；仓库 **100% 为净室原创源码**，零专有固件二进制分发 |

### 背后的四大工程考量

1. **考量一：单台主力机“零硬件调试口、零失败预算”的物理安全底线**  
   在既不拆机焊主板 UART、也没有外部 Fastboot 救砖短接线的真实条件下，直接改内核或核心库再烧录闪存，任何一次偏移失误都会导致不可逆变砖。因此我们坚持**不刷写内核与整包固件、先建 60s 双槽自动回滚守护再挂载业务、对未闭合所有权的硬件总线异常严格执行“宁可扣死租约隔离、绝不误放 DMA”的失效关闭（Fail-Closed）原则**。
2. **考量二：100% 净室（Clean-Room）开源洁净度**  
   不篡改、不重打包原厂二进制文件，使得所有仓库只需发布纯原创 C / ARMv7 ASM / Python 源码与确定性构建脚本，无需分发一字节厂商受版权保护的固件代码。
3. **考量三：用“原码无桩执行预言机”替代高危真机试错**  
   通过把原厂真实指令直接映射进 Unicorn 无桩环境与 QEMU 原厂动态加载器靶场执行，用原厂代码自身的位宽截断与状态机反例在接触硬件前淘汰错误假设。
4. **考量四：突破“改标志位”天花板，构建真正可扩展的插件底座**  
   当目标机型原厂代码中根本不存在某项能力（如无音频导入框架、UI 控件事件位全零、无多指手势状态机）时，单靠寻找隐藏开关已无能为力；唯有建立带电源休眠/唤醒屏障（`INACT / ACT`）的模块化底座，才能从零生长出完整的原生功能子系统。
